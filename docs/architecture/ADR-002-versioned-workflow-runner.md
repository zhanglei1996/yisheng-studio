# ADR-002：采用版本化后端工作流 Runner

## 状态

已接受，M1～M4 已完成；进入持续质量收紧。

## 背景

当前任务状态已持久化到 SQLite，但阶段执行入口分散在 React 队列页面和多个 Rust command 中。前端根据 `stage` 字符串选择媒体准备、ASR、翻译、TTS 或打开编辑器；Rust command 又会在完成后直接交接或调用下一阶段。随着人声分离、语义旁白、局部重生成和导出预检增加，同一流程存在多个控制者。

该结构短期直观，长期会造成：

- UI 与后端对“下一步”的理解漂移；
- 暂停、人工审核、失败重试和崩溃恢复的语义交叉；
- command 同时承担 IPC、用例、Provider、数据库和发布逻辑；
- 新工作流模式通过条件分支扩散，而不是扩展节点定义。

## 决策

在 Rust 核心中建立固定、版本化的工作流 Runner，逐步成为任务控制面的唯一权威。

第一阶段使用产品内置的静态有向无环图，不开放用户编排，也不引入通用工作流平台。节点至少包含：

- 稳定 `node_id` 与 `node_version`；
- 类型化输入、输出 Artifact 引用；
- `Completed`、`WaitingForInput`、`Retryable`、`Failed`、`Cancelled` 结果；
- attempt、进度、错误分类、开始/完成时间；
- 可取消性、资源类别和并发限制。

前端只能发送工作流意图：开始、继续、取消、提交审核决定和重试节点。前端可以根据节点状态选择界面，但不能决定后端下一节点。

## 持久化模型

在保留现有 `jobs` 表兼容视图的前提下，逐步引入：

- `workflow_runs`：工作流 ID、版本、项目、总体状态；
- `node_runs`：节点、版本、attempt、输入/输出引用和状态；
- `run_events`：脱敏的追加式生命周期事件；
- 现有 `artifacts`：继续作为内容寻址产物注册表。

运行事件用于恢复、诊断和投影当前状态，不把整个业务数据库改造成事件溯源系统。

## 迁移策略

1. 先引入类型化 `JobStage`，保持现有行为。
2. 建立 Runner 接口与内存/SQLite 合同测试。
3. 先迁移 `media -> asr -> translation`，旧 commands 作为兼容 facade。
4. 再迁移审核节点、TTS、对齐、混音和导出。
5. 当前端不再分发阶段后，删除旧阶段编排分支。

以上迁移已完成。当前生产定义版本为 4，媒体、ASR、审核、翻译、TTS、对齐、混音预览和外部导出发布均受 Runner 合同约束；旧 `jobs` 仅保留为兼容投影和编辑器用例状态边界。

## 不采用的方案

- **继续扩展 command 条件分支**：不能解决双控制面和恢复语义问题。
- **拆成网络微服务**：单机应用会承担额外部署、IPC、版本和一致性成本，隐私边界也更复杂。
- **立即引入第三方通用工作流引擎**：当前节点数量和单用户规模不需要其运维与抽象成本。
- **一次性重写**：会同时触碰媒体、Provider、数据库、UI 和真实凭据链路，回归面不可控。

## 后果

正向结果是状态权威统一、节点可测试、重试范围明确、诊断可重放，并为快速/审核模式共享同一流程骨架。代价是迁移期会同时存在兼容 job 投影与新运行模型，需要合同测试保证两者一致。
