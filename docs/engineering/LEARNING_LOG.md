# 译声工坊：工程难点与决策学习记录

这份文档记录项目中值得复盘的工程问题。目标不是罗列修改，而是解释：问题为什么难、证据如何建立、方案为何这样选，以及以后遇到类似问题时可以复用什么判断方法。

## 记录标准

以下情况应主动新增记录：

- 需要在多种架构方案之间做重要选择；
- 同时受到产品、性能、安全、成本或兼容性约束；
- 形成了可以在其他项目复用的设计方法或工程方法；
- 为解决复杂问题引入了新的模型、协议、数据结构或验证体系；
- 使用真实数据、性能测量或协议研究后，形成了重要技术结论。

Bug、故障报告、普通排查过程、日常重命名、格式调整、简单类型错误和机械性改动不进入此文档。Bug 只有在引出了独立且长期有效的架构方法时，才记录该方法本身，不记录 Bug 流水账。


## 2026-08-14｜非破坏音画编辑必须由单一时间映射驱动所有发布产物

状态：已解决

### 背景与难点

中文旁白若追求连贯，发声窗口可能长于原字幕窗口；只移动音频会造成画面错位，只裁视频又会让原声、字幕、预览和最终导出使用不同的时钟。项目还要求原视频不被改写、建议可撤销、低信息画面才能自动处理，并保留音乐和环境声。

### 证据与定位

新增的统一映射位于 `src-tauri/src/timeline_map.rs`。`src-tauri/src/localization.rs` 从语义间隔与 FFmpeg `freezedetect` 结果生成建议，`src-tauri/src/exporter.rs` 将同一映射应用于视频、原声、中文配音和全部字幕，`src-tauri/src/media.rs` 用它生成采用建议后的预览。真实样片成片为 608.688 秒且源 AAC 为单声道。

### 方案选择

没有直接改写媒体文件，也没有给每种产物各写一套减时逻辑。时间编辑以 source interval + operation + output duration 持久化，`TimelineMap` 编译成 source/output spans；裁剪、加速和后续字幕映射全部消费 spans。自动裁剪只有在语义停顿与静止画面相交时达到高置信度，快速模式才自动采用；其余仅建议加速或等待用户确认。音乐/掌声等事件从口播生成单元排除，原声音轨用中文配音作 sidechain 动态避让后再混合。

### 验证

- Rust 测试覆盖裁剪 ripple、加速区间映射、重叠编辑拒绝、静止画面高置信度裁剪和视频/原声共享 EDL。
- 真实 FFmpeg 回归将样片 3–5 秒裁去，10 秒输入得到 8.000 秒输出，视频与原声音频均来自相同保留区间。
- 发布输出显式 `-ac 2`，把单声道输入标准化为双声道 AAC；中文独立 WAV 也输出 48kHz 双声道。
- `pnpm verify:full` 覆盖构建、Rust tests、Clippy 和 rustfmt；本地浏览器完成时间轴与导出门禁视觉检查。

### 可复用经验

任何会改变总时长的媒体编辑，都应先定义一个可逆、可验证的时间映射，再让视频、所有音轨、字幕、标记和预览共同消费。FFmpeg filter graph 是映射的执行器，不应成为领域事实本身。自动删时必须同时证明“语义可删”和“视觉可删”；只满足一侧时应降级为加速建议或人工决策。

### 剩余风险

当前低变化检测使用冻结帧差阈值，对缓慢推镜或鼠标小幅移动会偏保守；后续可加入光流/场景信息密度评分。freeze 操作已进入领域模型但本轮没有自动生成，启用前需补充视频帧延长与音频留白策略。长片首次视觉扫描有 FFmpeg 成本，应按源文件指纹缓存区间。

## 2026-08-13｜让“可导出”成为共享的后端事实，而不是多个页面的猜测

状态：已解决

### 背景与难点

同一个本地视频项目同时存在流水线阶段、配音生成状态和时长适配状态。若项目库、队列、编辑器和导出弹窗分别拼接这些字段，就会出现“80%”“已暂停”“待处理 33”互相矛盾，甚至前端认为可以导出而后端仍缺少可用音频。还要满足两个不同规则：生成失败必须阻断；仅时长超窗可以知情导出。

### 证据与定位

共享契约位于 `src-tauri/src/domain.rs` 的 `ProjectReadiness`、`ExportPreflight`、`TtsFitResult` 和 `TtsFitProgress`。唯一导出判定由 `src-tauri/src/commands.rs` 的 `export_preflight_for_segments` 产生，并同时被 `project_readiness`、`export_preflight` 与 `export_start` 使用。自动适配不再返回裸 ID 列表，前端也不解析字符串检查点。

### 方案选择

考虑过只在 React 中写一个 selector，但它无法保护直接调用的 Tauri 导出命令，也会让任务队列与项目卡各自保留派生逻辑。最终将“阻断/提醒/能否导出/下一动作”收敛成后端领域对象；前端只负责按场景表达。批量修复的撤销快照保留完整口播文档和版本，撤销时恢复文本结构并把音频置为 `stale`，避免恢复文本却继续复用不匹配的旧音频。

### 验证

- Rust 单元测试覆盖“时长 warning 可导出、stale/failed 音频阻断导出”。
- `export_start` 在真正写出文件前再次执行同一预检，前端按钮状态不再是安全边界。
- 浏览器交互验证了问题定位、对齐面板与时长提醒的知情导出路径。
- `pnpm verify:fast` 与 `pnpm verify:full` 覆盖 TypeScript、Vite、Rust tests、Clippy 与格式检查。

### 可复用经验

跨页面状态应设计成可序列化的领域结论，而不是让每个界面组合底层标志。任何影响数据输出的“就绪检查”必须在后端执行，前端展示可复用其结果，但不能替代它。长任务进度应使用阶段枚举与数值事件，UI 文案是展示层映射，不应成为协议。

### 剩余风险

批量撤销快照当前属于进程内的“最近一次操作”，应用重启后不会保留；若未来要求跨重启撤销，应把快照升级为 SQLite 操作日志并定义清理周期。真实 33 段云合成的耗时、成本和部分失败分布仍需用脱敏项目做端到端回归。

## 2026-08-13｜时长适配必须同时保存“结果状态”和“可解释证据”

状态：已解决

### 背景与难点

配音片段有三层事实：云服务是否返回音频、音频是否能放进原视频时间窗、当前工程是否有可发布且与口播版本一致的片段文件。仅用 `warning/stale/failed` 组合无法直接推导用户文案；尤其当超时音频没有发布时，`ttsDurationMs` 为空，界面不能拿目标窗口冒充实测结果。另一方面，完全禁止轻微自动加速会让语义已足够精简的短片段陷入反复云合成。

### 证据与定位

真实 136 段项目中，批量压缩后剩余片段窗口为 4.08 秒，常规适配后音频约 4.62 秒，所需 tempo 约 1.13。数据库记录为 `status=warning`、`tts_state=stale`、`tts_duration_ms=NULL`，但旧 Inspector 回退到窗口时长并显示“适配良好”。关键实现位于 `src-tauri/src/commands.rs` 的云 TTS 发布判断、`src-tauri/src/tts.rs` 的窗口适配，以及 `src/components/Inspector.tsx` / `Timeline.tsx` 的证据展示。

### 方案选择

没有把所有 stale 都判为阻断，也没有无限制强制压速。最终规则是：显式 `status=warning` 属于时长提醒；缺少 `ttsDurationMs` 时 UI 只说“待适配”，不展示伪造数值；常规自然适配保持 1.08x，只有 32 字以内且所需 tempo 不超过 1.25x 的短片段可进入第二层不变调兜底。发布前仍计算内容哈希并原子替换，导出时继续校验整片混音依赖。

### 验证

- 同一真实片段以约 1.13x 兜底后得到 4.08 秒音频，136 个片段全部 ready。
- 实际播放中文合成预览，时间码正常推进。
- 本地导出产出 629.005 秒的 H.264/AAC MP4 和同长度 48kHz PCM WAV，另有三种字幕文件。
- Rust 导出预检测试覆盖 stale warning 可提醒导出、非 warning stale/failed 阻断；`pnpm verify:fast` 与 `pnpm verify:full` 覆盖前后端构建和静态检查。

### 可复用经验

状态枚举回答“下一步是什么”，可解释证据回答“为什么”。任何基于测量的 UI 都必须区分目标值、实测值和未知值，未知不能回退成看似成功的目标值。媒体自动修复应采用分层护栏：先内容压缩与温和处理，再对可证明安全的小范围启用有上限的兜底；超过边界继续请求人工决策。

### 剩余风险

短片段 1.25x 上限来自本次真实样本与自然度保守决策，尚未进行多音色盲听。后续应按音色/语言统计 MOS 或人工接受率，再决定是否把阈值做成服务商能力参数。导出器已改为自动选择未占用的版本目录，未来若增加覆盖模式，应继续默认保守并在写入前展示精确冲突清单。
# 从字幕时间单元到声学生成单元

## 背景与约束

字幕需要逐条保留，才能保证翻译校对、时间码和局部编辑能力；但把每条字幕直接当作一次 TTS 请求，会让模型在每句开头重置气息、音量和语气。对本项目 136 条字幕的 10 分 29 秒课程视频，逐句生成即使总静音量合理，听感仍呈现明显“片段感”。原视频和原声必须留在本地，云端只能收到必要的中文口播稿。

## 证据与方案比较

- 逐句结果的 `>=300ms` 静音为 171 个，`>=500ms` 静音为 110 个；但决定性问题是 136 次声学状态重置，不只是静音总量。
- 直接合成整篇能最大化连续性，却破坏局部重生成、时长定位与成本控制。
- 选定方案将字幕单元和声学生成单元解耦：字幕仍为 136 条；按间隔、跨度、最大条数和覆盖参数构建 5–15 秒连续语音块，本片得到 52 块。

## 实现

- `balanced_tts_blocks` 在间隔 >=1200ms、跨度 >=12s、加入后超过 15s、达到 6 条或 TTS 覆盖参数变化时切块。
- 每块一次阿里百炼请求，提示模型在句间保持相同气息和说话状态；按块做完整性校验、时长适配、内容哈希和缓存。
- 所在块的所有字幕共享块哈希。编辑一句时只扩展重生成该块，其余块从缓存复用；最终仍原子发布整条中文混音。
- 旧项目默认保持严格同步；新项目默认平衡模式。切换模式提升项目 TTS revision，并把旧音频标记为 stale，避免混用两种缓存。

## 验证

- `pnpm verify:full`：61 个 Rust 单元测试通过、1 个需媒体样本的测试忽略，7 个服务商契约测试通过；TypeScript、Vite、Clippy、rustfmt 均通过。
- 使用真实阿里百炼 `qwen3-tts-instruct-flash / Cherry` 完成 52 块合成；2 个超时问题经既有自动适配流程解决并成功导出。
- 平衡模式 `>=300ms` 静音降为 136 个，`>=500ms` 降为 81 个；视频时长保持 629.005 秒。

## 可复用结论与剩余风险

带时间轴的生成式媒体产品不应默认让“编辑单元 = 模型调用单元”。应把可编辑语义单元、声学生成单元、发布单元分开建模，并分别提供缓存与原子发布。剩余风险是块边界仍可能产生少量状态变化，且超长自然停顿可能增加；后续可用说话人嵌入或流式上下文进一步降低跨块差异。

## 2026-08-13｜连续配音的上下文窗口不能大于可校验的同步窗口

状态：已否决长章节方案，恢复短锚点方案

### 背景与难点

长上下文 TTS 能减少声学状态重置，但视频本身要求旁白语义在关键画面附近出现。两者不是同一目标：总时长相同不代表局部同步，章节越长，局部语速误差的积分越大。

### 证据与定位

真实 629.005 秒项目使用 Qwen3-TTS Realtime 将 136 条字幕合为 7 个约 60–100 秒章节。章节内声音连续性提升，但人工试听确认明显音画不同步；`silencedetect=noise=-42dB:d=0.30` 发现 7 个不少于 2 秒的静音，最长约 18.85 秒。`src-tauri/src/commands.rs` 的长章节分组和 `src-tauri/src/tts.rs` 的章节适配只能约束章节总长度，不能保证章节内部语义锚点。

### 方案选择

否决“整章统一变速填满窗口”：它能缩短章节尾部空档，却会继续把局部语义错位隐藏在章节内部。产品恢复 5–15 秒平衡块，并将其重新设为云项目默认和 UI 推荐。后续连续性优化限定在短块边界：相邻上下文提示、响度/音色归一和不跨语义锚点的短交叉淡化。

### 验证

- 在真实 App 中切回平衡模式，重新生成 52 个语音块。
- 自动适配最后 1 个超时片段后，136 个片段全部 ready，项目重新显示可导出。
- 长章节实验输出保留为对照，不覆盖此前用户认可的平衡模式视频。

### 可复用经验

生成式视频的同步质量必须用局部锚点约束，不能只验证轨道总时长。声学上下文可以跨块传递，但发布时间轴必须频繁重新锚定；“模型上下文窗口”和“允许漂移窗口”应是两个独立参数。

### 剩余风险

平衡块仍有块边界状态重置。下一轮应先做不改变时间轴的后处理与跨块上下文实验，并以语义锚点偏差和盲听连续性双指标验收，任何一项退化都不能作为默认方案。

## 2026-08-14｜配音设置切换应切换版本化音轨，而不是销毁当前生成状态

状态：已解决，缓存版本按真实合成输入自动失效

### 背景与难点

项目设置原先只有一组“当前 TTS 状态”。切换服务商、音色或连续性模式时，数据库会把所有片段标记为 stale；虽然按设置哈希命名的 WAV 仍保存在项目目录，生成器却同时要求片段状态为 ready，导致切回已经生成过的配置仍会重复请求云端。系统语音缓存键还包含单调递增的项目设置 revision，因此即使设置完全相同，切走再切回也无法命中。

### 证据与方案比较

- 直接保留 ready 状态不可行：当前混音和片段状态会谎称仍对应旧配置，导出可能混用音轨。
- 为每种配置复制整套片段表能够表达完整版本，但需要数据库迁移、版本 GC 和脚本编辑后的级联失效，超出实际所需。
- 现有内容寻址文件已经保存了每个逐句、语音块、章节或场景节拍版本。选定方案保留“当前状态单一、历史产物多版本”：设置切换时当前状态仍置 stale，但下一次激活先按真实输入哈希查找本地文件；命中后只重建当前混音和发布状态，缺失单元才调用 TTS。

### 实现

- 云端逐句、平衡块、连续章节和语义节拍的复用条件改为“目标哈希文件存在且有效”，不再依赖当前片段是否为 ready。
- 系统语音缓存键移除项目设置 revision，改为稳定包含音色、风格、设置 JSON、片段覆盖参数、脚本 revision 与口播文案；真实音频输入变化仍必然产生新键。
- `TtsRunResult` 增加 `cacheHitUnitCount`，任务检查点持久化 `cache:命中数/合成单元数`。前端切换设置后立即激活目标音轨，完整命中时提示未重复请求，部分命中时只补齐缺失单元。
- 快速模式在翻译后自动执行合成、一次失败重试和时长适配；再次打开仍有 stale/failed/warning 的快速项目时进行一次有签名防重的后台恢复。

### 验证

- `system_partial_run_restores_a_stale_unselected_clip_from_disk_cache` 证明 stale 状态不会阻止磁盘缓存恢复。
- `system_cache_key_is_stable_across_track_switches_but_changes_with_audio_inputs` 证明设置 revision 变化不破坏缓存，而速度覆盖变化会失效。
- `pnpm verify:fast` 通过 TypeScript、Worker 测试和 Rust 全目标检查；Browser 验证快速模式不再展示人工问题横幅，任务队列能看到当前模式与缓存复用结果，控制台错误为 0。

### 可复用经验与剩余风险

生成式媒体的“当前选择”与“已生成资产”应分开建模：前者可以失效，后者应由真实输入哈希长期复用。单调 revision 适合并发发布 CAS，不应进入可复用内容的身份键。当前方案切换完整缓存时仍会本地重混并刷新预览，这是为了保持原子发布和导出依赖一致；超大项目可进一步缓存整条混音以缩短本地切换时间，并需要后续增加容量上限和历史音轨清理策略。

## 2026-08-13｜语义重写窗口、声学生成窗口和发布时间轴必须分层

状态：已解决，持续观察主观听感

### 背景与难点

逐句翻译能守住时间码，却让每句像独立录音；长章节 TTS 能让声音连贯，却会把章节内部的语速误差累积成明显音画漂移。用户真正需要的是三个目标同时成立：中文不必逐字对应、讲解听起来像同一人连续完成、关键概念仍在相关画面附近出现。这三个目标不能由一个固定分块粒度同时满足。

### 证据与定位

真实样本有 136 条字幕、总长 629.005 秒。逐字幕声学调用有 136 次状态重置；60–100 秒长章节实验的最长静音达到 18.84 秒并被人工试听判定音画不同步。最终实现位于 `src-tauri/src/commands.rs`：翻译阶段先形成约 30–60 秒语义场景，再将口播发布到约 5–15 秒同步块；`src-tauri/src/translation.rs` 使用百炼结构化输出保留每个字幕 ID 的对应关系；`src-tauri/src/tts.rs` 继续对短块做有上限的时间窗适配。

### 方案选择

最终把同一素材拆成三种独立单元：

1. 语义重写单元使用较长场景，让大模型理解上下文、合并重复信息并使用自然中文讲解；
2. 声学生成单元使用相邻短块，让同一次 TTS 请求覆盖多句并减少气息和语气重置；
3. 发布时间轴仍用频繁的画面锚点约束，每块单独校验时长，避免章节内部漂移。

字幕译文与口播文案分开保存。大模型可以改写口播，但不能破坏字幕 ID、顺序和术语保护；云端只接收必要文本，不上传原视频或原音轨。生成任务支持从“语义改写完成”检查点继续，防止 TTS 中断后重复产生翻译费用。

### 验证

- 真实阿里百炼 `qwen-plus` 完成 12 个场景的语义改写，阿里 Qwen3 TTS 完成 52 个连续语音块；最终 136/136 片段 ready。
- 在 App 中播放中文合成预览并通过统一后端预检；实际导出 MP4、WAV 和三种字幕文件。
- 新版 WAV 与视频同为 629.005 秒。以 `-42dB / 0.35s` 检测，累计静音由上一可用版 124.80 秒降至 84.48 秒，最长停顿由 3.47 秒降至 3.18 秒；长章节方案的 18.84 秒空白不再出现。
- `pnpm verify:fast` 用于实现迭代，交付前运行 `pnpm verify:full`；视觉和真实操作证据记录在 `docs/design/qa/semantic-narration-2026-08-13/`。

### 可复用经验

生成式配音不应寻找一个“最佳分块大小”，而应分别定义理解上下文、声学连续性和同步校验所需的窗口。长上下文负责“说什么”，短声学块负责“怎么连续地说”，发布时间轴负责“什么时候说到”。结构化 ID 是把自由改写安全映射回可编辑时间轴的关键；缓存键和恢复检查点也应跟随这三层模型，而不是只跟随字幕行。

### 剩余风险

静音减少只能证明节奏更连续，不能完全替代母语者盲听；后续应记录场景级语义遗漏率、关键画面锚点偏差和跨块音色突变量。当前 TTS 仍是 52 次稳定 HTTP 合成，而不是一个跨全片的持久声学会话；若服务商提供可验证的会话状态或说话人嵌入，应在不扩大同步窗口的前提下接入。

## 2026-08-13｜媒体发布层必须验证时间区间不变量

状态：已解决

### 背景与难点

音频混合器允许多个输入同时存在，这是音乐、环境声和交叉淡化的正常能力；但同一旁白轨的相邻语音块同时存在，会被用户听成两个人说话。生成成功、文件可读、总轨长度正确都不能证明时间轴有效。语义配音尤其容易暴露这一点：模型给出的文字可能比建议长度长，温和的 1.08x 适配仍不足以装进画面窗口。

### 证据与定位

真实样本 4:23 处的前一语音块窗口为 247.88–259.06 秒，实际音频 19.36 秒，溢出 8.18 秒；下一块从 259.06 秒开始。`src-tauri/src/commands.rs` 曾在 semantic 模式强制把 `too_long` 设为 false，`src-tauri/src/tts.rs::mix_track` 使用 FFmpeg `amix`，因此该错误被合法混入最终 WAV。成片总长仍是正确的 629.005 秒，普通格式校验无法发现。

### 方案选择

没有在导出阶段截断音频，因为截断可能切掉句尾且无法修正文案。最终采用两层保护：生成层把超窗语义块恢复为可见 warning；发布层的 `validate_non_overlapping_inputs` 计算每个当前音频文件的真实时长，确保它在下一输入开始前结束，否则拒绝原子发布。自动处理以整个声学块为单位调用百炼压缩，允许跨字幕槽删除重复表达，同时保留全部稳定 ID 和字幕译文。

### 验证

- 新增 `publish_layout_rejects_overlapping_narration_blocks`，构造 1.2 秒音频在 1.0 秒处接入下一块，验证发布守卫拒绝重叠。
- 真实项目重新生成 52 个语音块，自动压缩后 136/136 ready；数据库按当前 `tts_settings_hash` 过滤历史产物，得到有效块 52、超窗块 0、最大边界误差 7ms。
- 4:23 邻域当前块为 247.88–259.06 秒窗口 / 9.23 秒音频，下一块 259.06–270.96 秒 / 11.58 秒。
- App 导出预检通过并实际导出 629.005 秒修复版视频。

### 可复用经验

媒体管线应在最终发布边界验证领域不变量，而不能假设上游已经处理：旁白轨区间不得重叠、内容哈希必须匹配脚本版本、所有必需区间必须有可用音频。FFmpeg 能执行某种混合不代表该混合符合产品语义。历史产物分析必须用当前依赖哈希过滤，否则会把旧缓存误判为当前结果。

### 剩余风险

当前允许 20ms 数值容差，用于抵消 WAV 时长舍入；未来若引入有意的短交叉淡化，应显式区分“同一连续发声的淡化边界”和“双内容重叠”，不能简单放宽全局阈值。自动压缩可能牺牲次要信息，仍需通过字幕保留完整语义并在 UI 提供撤销。

## 2026-08-13｜字幕发布时钟必须跟随最终口播音频，而不是识别片段

状态：已解决

### 背景与难点

语义重写允许跨原字幕行合并、删减和改述，因此“源字幕时间码 + 译文”不再等于“最终口播内容 + 发声时间”。继续烧录源时间轴会出现听到一句话时屏幕展示另一句，即使中文音轨本身完全同步。

### 证据与定位

`src-tauri/src/exporter.rs` 原先直接用 `SegmentRecord.start_ms/end_ms` 和 `subtitle_zh` 写出并烧录 `中文字幕.srt`。真实项目的 136 条同步字幕相对旧时间轴起点中位移动 169ms，极值为前移 3.752 秒、后移 3.209 秒；4:23 附近口播已把两个源分段重写为一句，但旧字幕仍逐行切换。

### 方案选择

发布层现在读取当前依赖哈希对应的 5–15 秒 TTS 块，以块的实际音频时长确定窗口，再按最终 `spoken_zh` 的阅读权重分配行边界，并优先吸附到 FFmpeg `silencedetect` 找到的停顿中心。块首尾静音用于收紧字幕可见区间，跨块边界再执行单调、不重叠校验。原 `中文字幕.srt` 保留为忠实翻译稿，新增 `配音同步字幕.srt` 作为视频默认烧录源。

没有把强制对齐模型设为导出必需依赖：本地 Whisper 只有英文模型，而安装多语言模型会增加体积和首次导出等待。当前方案利用生成阶段已知的文字顺序、TTS 块锚点和音频停顿，无需上传音频。未来可把 stable-ts/WhisperX 类词级强制对齐作为可选精校层。

### 验证

- Rust 单测覆盖静音日志解析、口播文案替代译文、块内时点分配和跨块字幕去重叠。
- 真实导出包同时包含配音同步 SRT、忠实翻译 SRT、英文 SRT、同步双语 ASS、WAV 和烧录同步字幕的 MP4。
- 4:23 邻域同步字幕为 259.171–267.489 秒，文本与实际合成口播一致；视频仍为单 AAC 音轨，总长 629.005 秒。
- 重复导出额外发现已完成任务不能重新入队；现允许导出命令安全重置同一已完成任务后再次执行。

### 可复用经验

只要发布文案与识别文案允许一对多、多对一或改写，字幕就必须成为最终音频的派生产物。忠实字幕和配音字幕服务不同目标，应分别保存和命名；前者保证内容完整，后者保证观看同步。

### 剩余风险

按文字权重并吸附停顿仍不是词级声学强制对齐。极少停顿、数字/英文术语密集或模型异常拉长某个词时，行内边界可能有数百毫秒误差。后续应把词级对齐作为可选增强，并记录字幕出现时间相对词首的 P50/P95 偏差。

## 2026-08-13｜跨 TTS 服务商切换必须迁移供应商命名空间状态

状态：已解决，讯飞整片实验完成

### 背景与难点

项目默认音色和片段音色覆盖是两层状态。音色 ID 不是跨服务商通用值：阿里的 `Cherry` 与讯飞的 VCN 属于不同命名空间。只更新项目默认服务商会留下历史片段覆盖，使界面看似已切换讯飞，实际请求仍把 `Cherry` 发给讯飞。

讯飞还把鉴权、字符额度和发音人授权分开校验。一次连接成功只证明当次 VCN 可合成；API 错误列出的枚举值也不代表账号已经购买该音色。因此静态音色目录、账号可用目录和项目选择不能混为一层。

### 证据

- 136 个历史片段均带 `{"voiceId":"Cherry", ...}` 覆盖；项目默认改为 `x6_lingxiaoxuan_pro` 后，首个整片块收到讯飞 10163（VCN 不合法）。
- `x7_susu_pro` 在接口枚举内，但短句实合成返回 11200 / `LiccCheck failed`；恢复账号原配置 `x6_lingxiaoxuan_pro` 后连接测试成功。
- 清除旧覆盖后，讯飞完成 52/52 个 5–15 秒语音块，零生成失败；其自然语速更慢，104 个片段 ready、32 个片段进入可修复时长 warning。

### 方案选择

`Database::set_project_tts_defaults` 在检测到服务商变化时，通过 SQLite JSON 操作只删除片段覆盖中的 `voiceId/voice_id`，保留 style、speed 和 directorEnabled。讯飞目录不再展示静态营销音色，只展示用户在服务商配置中填写的 VCN；服务商测试继续用真实短句合成校验当前音色。

管线把 10163、11200 和 `LiccCheck failed` 归类为确定性授权错误，首个请求失败后立即熔断，不再对余下 51 个块重复请求。错误提示明确引导用户回服务商配置并先做连接测试。

### 验证与可复用经验

新增测试覆盖跨服务商迁移只清理音色、不清理其他演绎参数，以及讯飞授权错误的不可重试分类。真实 App 中切换阿里 → 讯飞后，数据库 136 个 `voiceId` 覆盖归零，随后讯飞整片合成越过原错误并完成全部 52 块。

任何供应商可切换系统都应把模型、音色、区域、参数扩展视为带命名空间的状态。迁移不能只改顶层外键，也不能把服务商公开目录当作账号授权目录；至少要通过当前账号的最小真实调用验证选择，并对确定性配置错误做作业级熔断。

### 剩余风险

讯飞当前没有接入账号发音人目录 API，仍需用户从控制台复制 VCN。后续如服务端提供授权资源查询，应让目录标记“账号已验证”，并记录验证时间；不能仅根据文档或一次错误枚举自动声称可用。

### 完整实验结果

讯飞首轮合成完成后有 32 个片段所属块超窗；自动适配两轮解决 29 + 3 个，最终 52 个当前块全部使用 `x6_lingxiaoxuan_pro`，136 个片段 ready，最大块边界余量 248ms。实际导出视频和 WAV 均为 629.005 秒，视频只有一条 AAC 音轨。

以 `-42dB` 检测，讯飞 `>=300ms` 静音为 105 个 / 137.19 秒，阿里为 126 个 / 142.61 秒；但讯飞 `>=1s` 静音累计 112.14 秒，阿里为 101.57 秒。讯飞减少了零碎停顿，却把更多空白集中成较长间隔。讯飞原始综合响度为 -20.26 LUFS，阿里为 -23.74 LUFS；产品导出应统一做目标响度处理，不能把“更响”误判为“更自然”。

当前端到端两版口播稿字符数接近，但文本序列相似度为 0.769，说明语义重写存在抽样差异。结论只能用于比较完整产品链路：阿里拥有原生导演指令且时长适配压力更小，继续作为默认；讯飞可作为用户偏好音色的备选。若要做纯音色排名，必须固定同一稿件、同一块边界和同一响度后盲听。

## 2026-08-13｜Tauri 文件拖放应在 Webview 事件层收敛为媒体选择语义

状态：已解决

### 背景与难点

Web 前端的 `drop` 事件通常只提供浏览器 `File`，标准属性没有本地绝对路径；桌面媒体探测和后续处理却必须拿到原文件路径。macOS Tauri Webview 还会在系统层接管文件拖放，因此只给 React 容器绑定 `onDrop`，会出现界面像支持拖拽、真实桌面却不生效的错觉。

### 证据与约束

- 旧新建项目弹窗只有点击选择逻辑，没有 DOM 或 Tauri 拖放监听。
- `desktopBridge.probeMedia` 接受文件路径，而浏览器标准 `File` 不保证 `path`。
- Tauri 2 的 `Webview.onDragDropEvent` 在 `drop` 事件中提供路径列表；窗口配置同时提供 `dragDropEnabled` 开关。
- 产品要求原视频留在本地，不能为了绕过本地路径问题把文件上传到 Web 服务。

### 方案选择

第一步弹窗打开时注册当前 Webview 的原生拖放监听，关闭或离开第一步时注销；`enter/over/leave` 只驱动可见反馈，`drop` 要求一次一个路径并交给统一 `loadPath`。`loadPath` 先校验 MP4/MOV/MKV/M4V/WebM，再调用既有媒体探测，和文件选择器共用同一错误、忙碌与项目命名逻辑。浏览器预览保留 DOM 拖放回退，使设计 QA 能覆盖交互反馈；Tauri 窗口显式设置 `dragDropEnabled: true`，避免依赖版本默认值。

没有把监听注册在整个应用生命周期：只有新建项目第一步能消费视频文件，缩小了意外替换媒体的范围。也没有复制原文件，drop 只传递路径，继续满足 local-first 约束。

### 验证

- `pnpm verify:fast` 验证 TypeScript、Rust all-target check 和 Worker 测试。
- `pnpm verify:full` 验证生产 Vite 构建、74 个 Rust 单测与 7 个服务商契约测试、Clippy `-D warnings` 和 rustfmt。
- Browser 逐步验证新建项目 1–4 步，第一步文件选择进入同一 `loadPath` 后可继续，截图保存在 `docs/design/qa/project-library-cleanup-2026-08-13/`。

### 可复用经验与剩余风险

桌面 Webview 中，“拖入本地文件”不是纯 DOM 交互；应在平台事件层拿路径，再立即收敛到与文件选择器相同的领域入口。UI 层负责反馈和辅助回退，平台层负责可靠路径，业务层只认识一次一个已校验的媒体来源。

Browser 自动化不能构造 macOS Finder 的真实绝对路径拖放；这部分仍应在刷新后的独立 `.app` 或桌面集成测试中做最终端到端回归。本轮通过官方 API 类型、显式配置、生命周期注销和完整编译测试降低风险，但没有把浏览器合成事件冒充为原生 Finder 验收。
# 2026-08-14｜保留背景声时，安全边界必须绑定到“允许进入混音的轨道”

状态：已解决，真实长片分离效果继续验收

## 背景与硬约束

中文配音需要保留鼠标点击、音乐和环境声，但不能在中文停顿或 ASR 漏检区间突然恢复英文。仅按“讲话区间压低、无讲话区间恢复原声”无法同时满足两者：ASR/VAD 是概率结果，边界误差会直接变成可听见的原语言泄漏。安全模式还必须支持时间线裁剪，并保持原视频只在本地处理。

## 证据与方案比较

- 旧预览与导出把 `mute` 映射为源音频增益 `0.42`，因此所谓静音仍会听见英文。
- 恢复无说话区间的完整原声能保留 SFX，但任何漏检、词尾或停顿都可能带回英文，无法作为“安全”承诺。
- 中置声道相消成本低，却会损失居中的音乐/SFX，对非标准立体声也没有可靠保证。
- 选定本地模型分离：先生成仅含背景与音效的 `background-safe.wav`，随后所有预览和导出只允许该轨与中文人声进入混音。

## 实现

- `src-tauri/src/media.rs` 使用应用管理的 `audio-separator 0.44.5` 和 `UVR-MDX-NET-Inst_HQ_3.onnx` 生成背景轨；缓存清单绑定源文件指纹、模型与运行时版本。
- `src-tauri/src/exporter.rs` 为安全模式使用独立的视频时间映射，filter graph 不引用 `[0:a]`；背景轨和中文轨分别消费同一 `TimelineMap` 后再混合。
- FFmpeg 中同一中文轨既要驱动 `sidechaincompress`、又要进入最终 `amix` 时，必须先用 `asplit=2` 生成独立的 `[voice_sc]` 与 `[voice_mix]`。不能把同一个输出标签直接交给两个消费者；长片处理中会出现中文帧被 sidechain 分支消耗、最终只剩低电平背景残留的错误。
- `src-tauri/src/commands.rs` 将背景轨缺失或过期加入后端导出阻断，不能由前端按钮状态绕过。
- `mute` 改为真正只输出中文人声；`duck` 保留为明确有英文残留风险的兼容模式。
- 分离组件、模型或输出失败时任务停止，不允许回退到完整原声。

## 验证

- 单元测试断言安全模式与静音模式的音频 filter 不包含 `[0:a]` 或时间线原声标签，并断言安全视频映射不解码原音频。
- 缓存测试验证源指纹变化会使安全背景轨失效。
- 预览缓存清单额外绑定 `audio_mode` 与混音配方版本。混音图升级后旧产物必须失效，不能只用文件修改时间判断缓存可复用。
- 真实 608.7 秒视频中，错误混音与英文源音频前 35 秒相关系数约为 `0.999`；显式 `asplit` 后降至 `-0.0014`。英文 Whisper 模型从完整英文逐字稿变为仅报告 `speaking foreign language`，与中文源轨表现一致。
- `pnpm verify:fast` 覆盖 TypeScript、站点 worker 与 Rust 全目标检查；交付前继续执行 `pnpm verify:full`、独立 App 构建与真实媒体试听。

## 可复用经验

当产品承诺“某类内容绝不会进入输出”时，安全性不能依赖区间分类器的准确率，而应在媒体图上建立白名单：只有允许的轨道可以连接到最终混音。分类器可决定何时 duck、何时提示，但不能决定是否重新引入被禁止的源。媒体图中的扇出也必须显式建模；一条流承担“控制信号”和“可听信号”两个角色时，要先 split 再分别消费。缓存必须携带产生安全轨道和最终混音的依赖证明，否则旧产物可能在源文件、模型或滤镜变化后继续被误用。

## 剩余风险

声源分离可能让极少量人声以音乐伪影形式残留，也可能削弱与人声频谱重叠的点击或音乐；“安全”表示不主动回混完整原声，不等于模型达到密码学意义的零泄漏。后续应增加残余语音检测、抽样试听门禁，并在更复杂音乐/多人说话样本上评估模型升级。

## 2026-08-14｜长任务阶段类型化必须同时封住 IPC、持久化与进度回调

状态：M0 基线已完成，Runner 迁移尚未开始

### 背景与硬约束

当前长任务由前端、Tauri command、媒体进度回调和 SQLite 共同推进。阶段原先是普通字符串，因此新增或拼错阶段可以越过编译器，直到恢复任务或页面分发时才表现为错误。改造又必须兼容现有数据库中的合法阶段，不能为了类型安全重建用户项目。

### 证据与方案比较

- 阶段值同时出现在任务创建、状态比较、媒体进度、数据库 checkpoint 和 Tauri 参数中，只改 `JobSummary` 字段会留下多个字符串入口。
- 媒体准备包含 `source_separation`，说明阶段集合并不等于旧页面里最常见的几个分支；靠手写多处联合类型仍可能漂移。
- 保留 `String` 并在运行时提供默认值最兼容，但会把未知数据库值伪装成合法状态；直接改为通用工作流框架则超出第一阶段范围，难以隔离回归。

### 选择与实现

Rust 以带 snake_case 序列化的 `JobStage` 作为唯一后端阶段类型，数据库写入统一调用 `as_str()`，读取使用严格 `TryFrom<&str>`；未知值在 SQLite 边界返回数据转换错误，不做猜测或回退。Tauri command 参数和媒体进度回调也使用该枚举，前端以同集合的 TypeScript 联合类型约束持久任务。

同时加入增量架构门禁：新生产文件默认不超过 500 行，已有大文件按当前规模设置不可增长预算；SQL 只允许在数据库基础设施模块，直接 Tauri invoke 只允许在 bridge，Rust 任务构造、比较和持久化禁止裸阶段字符串。门禁带有违规代码样例自检，并接入 `verify:fast`。

### 验证

- 数据库集成测试直接写入 `guessed_future_stage`，确认读取任务明确失败。
- 门禁自检覆盖直接 invoke、越层 SQL、裸阶段构造、比较和 checkpoint 调用。
- `pnpm verify:fast` 通过 TypeScript、Worker、架构门禁和 Rust all-target/all-feature check；完整测试结果见本次交付记录。

### 可复用经验与剩余风险

状态机类型化的边界不是结构体字段，而是所有能够生产、传输或恢复状态的入口。兼容旧数据不等于接受未知数据：对已知历史值显式枚举、对未知值尽早失败，才能让迁移问题可观测。机械门禁适合防止旧耦合继续增长，但不能代替领域拆分。

Rust 枚举和 TypeScript 联合类型目前仍是两份声明，后续应从共享 schema 生成 IPC 合同或加入跨语言一致性测试。现有 `JobSummary` 仍是可变状态快照；M1 需要用版本化运行事件投影它，才能完整解决崩溃恢复、幂等发布和取消竞态。

## 2026-08-14｜可恢复 Runner 应分离执行历史、当前状态与兼容投影

状态：M1 最小内核已完成，真实业务节点尚未迁移

### 背景与硬约束

旧 `jobs` 行同时承担当前进度、恢复检查点和 UI 展示。若直接在其上增加 attempt、节点版本和输入/输出 Artifact，既会让一行记录持续覆盖历史，也无法回答“某节点是否已经用同一版本成功发布过”。但一次性替换旧任务模型会同时影响 Queue、Editor 和现有长任务，违背渐进迁移要求。

### 证据与方案比较

- 仅保存 `current_node` 可以恢复位置，却无法区分第一次失败、重试和升级后重跑。
- 仅追加事件可以重放全部历史，但每次 UI 查询都重算任务状态，在当前单机规模没有必要把整个业务库改造成事件溯源系统。
- 直接让 Runner 依赖 rusqlite 会把执行策略和存储实现绑定，fake store、内存测试和后续替换 Repository 都会变困难。

### 选择与实现

M1 将三类职责分开：`workflow_runs` 保存运行当前状态，`node_runs` 保存不可覆盖的节点 attempt，`run_events` 保存追加式生命周期与兼容投影。Runner 只依赖 `WorkflowStore`；SQLite 实现在 infrastructure 中，旧 `JobSummary` 从最新 `job_projection` 事件反序列化，而不是让新内核反向写入旧 `jobs` 控制面。

节点以 `node_id + node_version` 识别完成结果。驱动器重开后先读取已成功 attempt，将其输出 Artifact ID 注入依赖节点并跳过执行；运行中断时，SQLite 启动恢复把 `running` 节点改为 `retryable`，保留 attempt 和 checkpoint，由显式 resume 创建下一 attempt。等待人工输入与可重试失败分别建模，不能复用普通 pause。取消同时有内存 `CancellationToken` 和持久化 `cancel_requested`，节点返回完成后仍会复查内存取消，避免把取消竞态中的结果记为成功。

### 验证

- fake nodes 覆盖定义依赖校验、完成、终止失败、等待审核、显式继续、取消令牌和持久化取消。
- 临时 SQLite 关闭并重新打开后，已完成媒体节点调用次数保持为零，后续 ASR 节点从第二个 attempt 成功；其输入仍包含第一次发布的 Artifact ID。
- 人为留下 `running` node run 后重开 Store，运行与节点均恢复为 `retryable`，兼容 `JobSummary` 投影为 paused，并产生 `run_recovered` 事件。
- 同一成功 run 重复驱动不会新增 node run，也不会重复返回新的 Artifact 发布结果。

### 可复用经验与剩余风险

可恢复执行器需要同时拥有三种视图：追加历史用于审计和诊断、当前行用于高效调度、兼容投影用于渐进迁移。幂等的判断对象不是“任务是否完成”，而是“同一节点版本在同一运行中是否已有成功 attempt”；下游输入必须来自那次成功记录，而不是重新扫描文件目录。

M1 仍只持久化 Artifact ID，没有统一 staging/原子发布服务；真实节点如果在返回 `Completed` 前自行发布文件，取消令牌无法撤销外部副作用。M2/M3 接入时必须要求节点先写 staging，由 Runner 在状态和 revision 再校验后发布。当前 DAG 使用定义顺序作为拓扑序，也暂未实现资源调度器和延迟重试计时器；这些应在真实节点迁移时按需要增加，不能提前扩展成通用工作流平台。

## 2026-08-14｜工作流收口必须同时迁移控制权、发布边界和用户输入边界

状态：M2～M4 已完成

### 背景与硬约束

真实媒体、ASR、翻译和 TTS 已有大量经过验证的算法，风险不在“重写算法”，而在谁决定下一步、失败后从哪里恢复、取消时哪些副作用允许发布。导出又必须等待用户选择目录和字幕模式，不能为了追求全自动 DAG 把交互输入藏回 React 阶段分支。迁移期间还必须继续向旧 Queue/Editor 投影 `JobSummary`，不能破坏已有项目。

### 证据与方案比较

- 只把 `QueuePage.runPersistedStage` 搬到一个大 Rust `match`，虽然移除了前端分支，却没有节点版本、attempt、输入产物和恢复语义。
- 让每个真实节点立即重写所有媒体/Provider 算法，回归面覆盖 FFmpeg、凭据、网络协议、缓存和时间轴，无法在一次迁移中可靠验证。
- 把导出节点提前标记成功会让 run 与用户实际拿到的文件不一致；让节点永久等待但没有外部完成协议，又会使已成功导出的任务永远显示未完成。
- 仅依赖文件 rename 不能覆盖“文件已替换、数据库事务失败”的窗口；仅依赖数据库事务也无法回滚文件系统。

### 选择与实现

生产工作流使用版本 4 的固定 DAG，真实节点复用已验证的媒体和 Provider 用例，但控制权只属于 Runner。快速与审核模式共享节点序列，区别只在审核 gate 的第一次 attempt 是否返回 `WaitingForInput`。前端只发送 enqueue/start/continue/retry/pause/cancel；架构门禁拒绝持久化 stage 分发，并检查旧处理 command 不再出现在 Tauri handler。

导出建模为外部输入节点：Runner 到达 `export_publish` 后持久化等待状态；用户从编辑器选择参数并成功导出后，Store 在同一事务中将等待中的 node attempt 和整个 run 标记成功，重复完成保持幂等。这样“等待用户参数”和“导出算法失败”都不会伪装成工作流成功。

文件系统发布由 `AtomicArtifactPublisher` 统一：staging 必须与目标同卷，文件先做非空校验；旧文件改名为 backup，新文件 rename 后执行数据库提交，提交失败恢复 backup。完整导出使用 RAII staging 目录，任何 `?` 提前返回都会删除半成品，成功时一次 rename。生产 Runner 还用全局 permit 服从旧 SQLite 单运行约束，并按 CPU/Media/Network/Disk 分类限流；每个真实节点记录资源等待和执行耗时。

### 验证

- Runner/SQLite 测试覆盖跨重启跳过已完成节点、失败重试、审核恢复、取消和外部导出幂等完成。
- Artifact 测试验证空文件拒绝发布、数据库提交失败恢复旧文件、未提交导出目录自动清理。
- 架构门禁验证前端不存在 stage 执行分发，旧媒体/ASR/翻译/job 手工交接 command 不再暴露。
- 使用 FFmpeg 生成 2.5 秒、640×360、带 AAC 音轨的真实 MP4，实际执行 probe、16 kHz PCM 抽取和代理生成；产物与阶段检查通过。
- `pnpm verify:fast` 覆盖 TypeScript、架构、Worker 与 Rust 全目标编译；最终交付执行 `pnpm verify:full`。

### 可复用经验

工作流迁移的完成标准不是“出现了 Runner 类”，而是三个权威同时收口：下一步由后端 DAG 决定，副作用由统一发布边界决定，用户输入通过显式等待/恢复合同进入。外部动作如果属于工作流的一部分，应有幂等完成协议，而不是用 UI 状态猜测它是否发生。

渐进迁移可以复用成熟算法，但只能把它们当节点内部实现；旧实现不得继续自行调用下一阶段。资源限制还必须服从遗留数据库约束：节点分类并发再精细，如果旧表只允许一个 running job，就需要在更外层保留一个全局 admission permit。

历史数据迁移也不能只看“是否存在 workflow run”。实机数据库中可能已有停在 TTS、对齐或导出的旧任务；若直接为它补建新 run，会从媒体准备开始重复昂贵且可能不可逆的处理。迁移入口因此先按旧任务状态和阶段分类：早阶段 queued/failed 任务允许由 Runner 接管，晚阶段 paused/waiting 任务映射为编辑器输入边界，已成功或已取消任务保持终态。该规则通过旧导出任务不会重启媒体、早阶段任务仍可接管的回归测试固定下来。

### 剩余风险

当前真实算法仍有较大部分位于 `commands.rs`，虽然已不再作为生产队列 IPC 入口，但还需要继续迁入 application services。节点内的长翻译批次和场景 TTS 仍使用内部 checkpoint，尚未拆成独立子节点。在线 ASR 模型、翻译和云 TTS 需要本机 Runtime 与用户凭据；自动验证覆盖合同、缓存和错误边界，不能代替带真实账号的内容质量验收。

## 2026-08-15｜长链路的“可恢复”必须同时覆盖云端费用、本地文件权限和导出语义

状态：真实阿里 TTS 英转中项目已完成断点恢复、混音和成片导出验收

### 背景与硬约束

真实项目有 162 个字幕片段、数十个云端语音块和约 10 分钟成片。失败后如果全量重跑，会重复产生阿里 TTS 费用；如果只依赖原始文件路径，macOS 打包 App 重启后的一次性文件选择权限又可能不再能被 FFmpeg 子进程使用。最后，导出是外部发布节点；文件已经原子提交后，工作流投影失败不能反向告诉用户“导出失败”。

### 证据与方案比较

- 同一次 TTS 运行的旧 CAS 快照包含会被自身 checkpoint 改变的状态，导致第二个语音块开始就与自己冲突。同时，重复保存完全相同的 TTS 设置会增加 revision 并把已完成音频全部标为 stale。
- 实机断点恢复后，任务能复用已落盘语音块，从 161 个 stale 收敛到仅重试未完成项，而不是再次全量请求云端。
- 首轮导出中，FFmpeg 子进程超过 2 分钟停在 `open(2)`，没有打开任何输入或创建 MP4；命令行手动执行则正常。进一步采样显示，打包 App 不仅无法让子进程重开原路径，尝试对该路径 `linkat` 也会阻塞。
- 备选包括：持久化 security-scoped bookmark、导入时复制整个原视频、导出时重读原路径，或使用媒体准备阶段已发布的本地代理。前两者需要新的权限/存储合同，第三种已被实机证明不可靠；当前产品已有最高 720p 的持久本地代理，可作为稳定发布输入。
- 第一份成片暴露另一个完整性问题：块级 Artifact 只能为 162 个片段中的 22 个生成当前依赖哈希匹配的字幕 cue。如果“有一部分精确 cue”就不再回退，会比完全没有精确 cue 更危险，因为大量缺失被伪装成成功。

### 选择与实现

TTS 块发布改为逐块数据库 checkpoint，运行快照只校验用户会改变的文案/设置，不再把运行自身写入的 `tts_state` 当作外部冲突。设置和服务商保存改为幂等：只有真正影响合成的字段改变才增加 revision。重试范围为所有未 ready 语音片段，已完成块直接复用。

导出不再读取外部原路径，而是优先使用 `media::prepare` 已发布的 `preview-proxy.mp4`；导出面板同步如实标示“本地预览画质（最高 720p）”，不再宣称 1080p。导出暂存目录在下次重试时自动清理，音频 staging 路径保留真实媒体扩展名以便 FFmpeg 推断格式。成片、字幕和音轨已提交后，只在 Runner 确实等待 `export_publish` 时更新外部节点；投影异常不再覆盖用户已拿到的成功结果。

配音同步字幕对块级 cue 采用“全覆盖才信任”：只有 cue 数与所有有口播片段一致时才使用块级精确时间；部分覆盖会回退到完整的片段时间线，保证不丢口播内容。

### 验证

- 数据库回归测试覆盖“相同设置不会使 ready 音频过期”和“同一快照可以连续发布多个语音块”。
- Artifact 测试覆盖媒体扩展名保留、中断暂存目录清理和本地代理优先选择。
- 字幕测试覆盖部分 cue 自动回退为完整片段集。
- `pnpm verify:fast` 通过 TypeScript、Worker、架构门禁与 Rust 全目标检查；交付前再执行 `pnpm verify:full`。

### 可复用经验与剩余风险

“可恢复”不是只记一个进度数字，而是三类合同：费用合同决定不重复调用哪些云端单元，权限合同决定重启后哪些本地文件仍可读，发布合同决定哪个结果已经不可被后续投影回滚。对部分完整性的判断应使用“全覆盖才启用精确模式”，而不是“有一点就用”。

当前稳定导出使用最高 720p 本地代理，这是已验证的权限/可恢复折中，不是最终画质上限。如要支持原分辨率跨重启发布，需要引入持久化 security-scoped bookmark 或导入时的明确“保留原片副本”存储策略，并将磁盘成本和画质选择暴露给用户。
